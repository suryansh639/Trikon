# Implementation Plan: trikon-cloud-fargate-runner

## Overview

M1 net-new component of Trikon Cloud — the ECS Fargate task runner that owns the `sdk.verify(...)` invocation and the GitHub feedback write. Ships a Python 3.11 container image extending `suryansh639/trikon:0.3.6` with a thin entrypoint that reads the memo §5.4 env-var contract, shallow-fetches the target repo, invokes `trikon.sdk.verify(no_sandbox=True)`, persists the verdict to DynamoDB via a conditional PutItem (with S3 spill for evidence blobs over 350 KB), and posts a byte-identical Markdown summary to both a Check Run and a PR comment. Grounding reference: `.kiro/specs/trikon-cloud-architecture/design.md` §3.1 (Fargate), §3.4 (DynamoDB shape), §3.5 (secrets), §3.6 (Check Runs), §3.8 (us-east-1), §3.9 (no ingress VPC), §4 (full data model), §5.3 (RunTask shape), §5.4 (env-var contract), §5.5 (PutItem shape), §5.6 (GitHub REST shape), §6 (security model + per-installation IAM), §7 (ECR Public migration is a task in this spec), plus cross-cutting Invariants 1-8.

Tech stack (per design.md §3): Python 3.11 in a Docker container extending `suryansh639/trikon:0.3.6`; `trikon==0.3.6` as a runtime dep (unlike Spec 1, this spec imports the SDK); `httpx>=0.27,<0.29` for GitHub API; `PyJWT[crypto]>=2.9,<3` for the App JWT; `pydantic>=2.9,<3` + `pydantic-settings>=2,<3` for models; `boto3>=1.35,<2` for DynamoDB + Secrets Manager + S3; `structlog>=24,<26` for structured logging (NOT aws-lambda-powertools — Fargate is not Lambda); `pytest` + `moto` + `respx` + `hypothesis` + `pytest-cov` for tests; AWS CDK (Python) for IaC. Package location: `trikon_cloud/fargate_runner/` — a new subpackage sibling of Spec 1's `trikon_cloud/webhook_receiver/`. Added to the existing `cloud` optional-dep group in `pyproject.toml` (created by Spec 1).

Wave partitioning: Wave 0 lands the package skeleton and extends `pyproject.toml`'s existing `cloud` group with this spec's new deps. Wave 1 lands the eight independent leaf Python modules where possible (`models.py`, `logger.py`, `summary_builder.py`, `token_cache.py` are pure leaves; `git_ops.py`, `dynamodb_writer.py`, `github_client.py` depend on models + logger). Wave 2 lands `entrypoint.py` (depends on all IO modules + `sdk.verify` wiring). Wave 3 lands the Dockerfile + CDK stack + CDK app entry. Wave 4 lands the test conftest + test modules (Properties 1-3 + edge cases + per-module unit tests). The checkpoint runs `docker build` (smoke, no push), `cdk synth`, mypy strict, ruff, pytest with the coverage bars.

Convert the feature design into a series of prompts for a code-generation LLM that will implement each step with incremental progress. Make sure that each prompt builds on the previous prompts, and ends with wiring things together. There should be no hanging or orphaned code that isn't integrated into a previous step. Focus ONLY on tasks that involve writing, modifying, or testing code.
