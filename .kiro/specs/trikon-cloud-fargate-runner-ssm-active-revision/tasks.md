# Implementation Plan: trikon-cloud-fargate-runner-ssm-active-revision

## Overview

Amendment to Spec 2's `FargateRunnerStack` that inserts exactly one `AWS::SSM::Parameter` at `/trikon/verify-runner/active-revision` so Spec 3's `TaskDefinitionResolver` can discover the current verification-runner task-definition revision at cold start. Ships one CDK edit to `trikon_cloud/fargate_runner/infra/fargate_runner_stack.py` (two import additions, one construct block, one `add_dependency` call, one class-level attribute), one new dedicated synth-time test file at `trikon_cloud/fargate_runner/tests/test_ssm_active_revision.py`, and one README amendment adding a `## 8. Deploy Ordering` section to `trikon_cloud/fargate_runner/infra/README.md`. Zero runtime Python changes, zero IAM changes, zero modifications to Spec 2's existing 77 tests.

Execution proceeds in three waves. **Wave 0** (task 1) lands the CDK edit — this is the only production-code change in the spec. **Wave 1** (tasks 2-3) lands the dedicated test file and the README section in parallel; they touch disjoint files and share no state. **Wave 2** (task 4) is the completion checkpoint: `pytest` (81 = 77 + 4), `mypy --strict`, `ruff check`, and a `cdk synth` inspection of the emitted template.

Convert the feature design into a series of prompts for a code-generation LLM that will implement each step with incremental progress. Make sure that each prompt builds on the previous prompts, and ends with wiring things together. There should be no hanging or orphaned code that isn't integrated into a previous step. Focus ONLY on tasks that involve writing, modifying, or testing code.
