# Requirements Document

## Introduction

Trikon v0.3.5 landed the `LocalSubprocessSandbox.exec` `--cache-dir=` argv strip that fixed the `--no-sandbox` static-analysis divergence on repositories with no pre-existing `.trikon/state.db`. Post-ship verification against `trikon==0.3.5` on PyPI + `suryansh639/trikon:0.3.5` on Docker Hub surfaced a second-order regression the v0.3.5 fix does not close: a user who upgrades from Trikon ≤ v0.3.4 to v0.3.5 with a pre-existing `.trikon/state.db` observes cache-poisoned verdicts on the first post-upgrade `trikon verify --no-sandbox` invocation. The `static_baseline` table in that DB carries rows written by the pre-v0.3.5 codebase whose `findings_json` payload is `[]` — the head-side finding-diff logic in `trikon.verify.static_checks._resolve_base_keys` classifies every real head-side finding as `is_new=True` against that empty baseline, flipping the verdict counters in a way that both inverts the `decision` (from `block` to `require_human` via the aggregate-count rule surface) and silently drops the `preexisting_errors` bucket to zero.

Concrete repro from the v0.3.5 post-ship checkpoint on WSL Ubuntu-22.04 (double-confirmed against `trikon==0.3.5` on PyPI + `suryansh639/trikon:0.3.5` on Docker Hub):

- Repository: `~/click` (pallets/click clone), base `87f7a31`, head `6aabf09`.
- Pre-condition: repo carries a `~/click/.trikon/state.db` (253,952 bytes, SQLite format) written by a pre-v0.3.5 `--no-sandbox` verify invocation.
- With `state.db` present: v0.3.5 `--no-sandbox` verify returns `new_errors=130, new_warnings=0, preexisting_errors=0`. Every finding is classed as new. `decision` is inverted relative to the ground truth.
- After `rm ~/click/.trikon/state.db`: v0.3.5 `--no-sandbox` verify returns the ground-truth verdict `new_errors=33, new_warnings=8, preexisting_errors=97` — matching the Docker path exactly on the same commit range.

The `rm state.db` step is required for a correct verdict; it should not be. A user reading the changelog for v0.3.5 has no reason to expect they must delete their state.db to observe the fix. The observed poisoning is silent — the return value of `sdk.verify(...)` is well-formed, the audit-log row is well-formed, no error is raised — so a CI pipeline that trusts the counters will see wrong data and take the wrong action.

The fix in this spec is a one-time-per-user schema-versioning migration hosted in a new module `trikon.verify.state_migrations`. It is hooked into `trikon.verify.runner._open_state_db` immediately after `ensure_verify_tables(conn)` and immediately before the connection is returned to the caller. The migration introduces a Phase-2-specific version marker `schema_meta.verify_schema_version` — independent of `schema_meta.schema_version`, which is owned by Change-Intelligence (Phase 1) and stays at `1`. On any state.db that lacks the marker, the migration issues `DELETE FROM static_baseline`, stamps `verify_schema_version = '1'`, and — when the delete affected one or more rows — emits a single-line WARNING-level log record on the `trikon.verify.state_migrations` logger naming the count of rows dropped and the reason (`Trikon < 0.3.6 pre-migration static_baseline cache`). On any state.db that already carries the marker, the migration is a no-op — a subsequent `trikon verify` invocation reads the marker, takes the fast path, and returns without touching `static_baseline`.

The exact upstream mechanism by which pre-v0.3.6 rows reached `static_baseline` with `findings_json = '[]'` is not further disambiguated in this spec. The bugfix invariant — "any `static_baseline` row that predates Trikon v0.3.6 is unusable and MUST be dropped from the cache before it can be read by the head-side finding-diff" — is invariant across the possible upstream mechanisms (empty stdout from failed cache init on the pre-v0.3.5 head-side subprocess, incomplete PATH augmentation in an earlier `_run_baseline_tool_on_host`, or any other pre-fix path that persisted an empty findings blob). The schema-versioning discipline (§Requirement 2) is what makes this invariant enforceable independently of the mechanism.

This is a **bugfix**. Public API shapes are unchanged: `sdk.verify(...)` signature, the `Verdict` fields, the CLI flag surface (`trikon verify`, `--no-sandbox`, `--policy`, `--diff-file`, `--output`), `LocalSubprocessSandbox.__init__` / `exec` / `mount_repo`, the `Sandbox` union alias, `SandboxExecResult`, and the `static_baseline` table columns (`id`, `base_sha`, `tool`, `tool_version`, `findings_json`, `computed_at`) all keep their v0.3.5 shape. `ensure_verify_tables` continues to be additive-only (`CREATE TABLE IF NOT EXISTS` and `CREATE INDEX IF NOT EXISTS` only). The migration operates on rows, not schema — it issues `DELETE FROM` and `INSERT INTO schema_meta`; no `ALTER TABLE`, no `DROP TABLE`, no `DROP INDEX`.

The v0.3.6 release commit that lands this bugfix will also bump `pyproject.toml` `version = "0.3.5"` → `version = "0.3.6"` and update four sandbox image tag references from `:0.3.5` → `:0.3.6` (`trikon/verify/sandbox.py`, `trikon/verify/runner.py`, `trikon/verify/_plugin_shim.py`, `Dockerfile.sandbox`). That is release plumbing — not this spec's scope. The task list acknowledges it as a follow-up for the release engineer, NOT part of the implementation tasks.

## Glossary

- **Trikon**: The product this codebase implements — the verification layer for autonomous AI coding agents. Consistent product name across every requirement (not "AgentGuard").
- **State_DB**: The SQLite file at `<repo>/.trikon/state.db` shared across Change-Intelligence (Phase 1), Verification-Runner (Phase 2), and Policy-Engine (Phase 3). Owned by no single subsystem; each subsystem is expected to open, read, and write its own sibling tables through the shared connection.
- **Static_Baseline_Table**: The SQLite table named `static_baseline` in State_DB. Schema fixed by `trikon.verify.db.ensure_verify_tables`: `(id INTEGER PRIMARY KEY AUTOINCREMENT, base_sha TEXT NOT NULL, tool TEXT NOT NULL, tool_version TEXT NOT NULL, findings_json TEXT NOT NULL, computed_at TEXT NOT NULL, UNIQUE (base_sha, tool, tool_version))`. Written by `trikon.verify.static_checks._resolve_base_keys` on cache miss; read by the same function on cache hit.
- **Schema_Meta_Table**: The SQLite table named `schema_meta` in State_DB, created by `trikon.change_intel.dep_graph.DepGraph._init_schema` with DDL `CREATE TABLE IF NOT EXISTS schema_meta (key TEXT PRIMARY KEY, value TEXT NOT NULL)`. Phase 1 seeds three rows on fresh-DB creation: `("schema_version", "1")`, `("created_at", <ISO>)`, `("trikon_version", <trikon-version-at-create-time>)`. This spec adds a fourth row `("verify_schema_version", "1")` starting in Trikon v0.3.6.
- **Phase_1_Schema_Version**: The integer stored under `Schema_Meta_Table` key `schema_version`. Owned by `trikon.change_intel.dep_graph.CURRENT_SCHEMA_VERSION` (currently `1`). NOT touched by this bugfix.
- **Verify_Schema_Version**: The NEW `Schema_Meta_Table` key added by this bugfix. Value `'1'` in Trikon v0.3.6. Owned by `trikon.verify.state_migrations.CURRENT_VERIFY_SCHEMA_VERSION` (initial value `1`). The Phase-2 version marker is independent of Phase_1_Schema_Version — the two evolve on separate cadences.
- **State_Migrations_Module**: The NEW module `trikon.verify.state_migrations`. Introduced by this bugfix. Public function `maybe_migrate_verify_state(conn)` returns `None` on success, raises `VerificationRunnerError` on failure.
- **Open_State_DB_Site**: The private function `trikon.verify.runner._open_state_db(state_db: Path) -> sqlite3.Connection`. Invoked from `trikon.verify.runner.run_verification`. The sole insertion point in this bugfix's implementation surface — the migration is called from here immediately after `ensure_verify_tables(conn)`.
- **Migration_Notice_Logger**: The Python logger `logging.getLogger("trikon.verify.state_migrations")`. Emits exactly one WARNING-level log record on the migration path when the `DELETE FROM static_baseline` statement affected at least one row.
- **Poisoned_Row**: A row in Static_Baseline_Table written by any Trikon build that did not stamp Verify_Schema_Version in Schema_Meta_Table. Operationally: "any row present in a State_DB whose Schema_Meta_Table does not contain the key `verify_schema_version`". The definition is deliberately schema-driven — not payload-driven — so a genuinely-clean baseline (`findings_json = '[]'`) written by v0.3.6 or later is NOT classified as a Poisoned_Row.
- **Migration_Notice_Message**: The exact human-readable string emitted by Migration_Notice_Logger when the migration drops rows. Format: `Trikon v0.3.6 dropped N stale row(s) from static_baseline (Trikon < 0.3.6 pre-migration cache; see spec static-baseline-cache-poisoning-migration).` where `N` is the row count reported by `cursor.rowcount` after the DELETE.
- **Click_Repro**: The pallets/click repository at base `87f7a31` → head `6aabf09`. The reference ground-truth verdict on Trikon v0.3.6 post-migration is `decision=block, matched_rule="new static-analysis errors", new_errors=33, new_warnings=8, preexisting_errors=97` on both the Docker sandbox path and the `--no-sandbox` path.
- **VerificationRunnerError**: The base exception class `trikon.verify.errors.VerificationRunnerError`. All migration failures wrap the originating `sqlite3.Error` (or `ValueError` from a corrupt `verify_schema_version` value) as `VerificationRunnerError` with `raise ... from exc` preserving `__cause__`, matching the Never_Fail_Open_Contract.
- **Never_Fail_Open_Contract**: The Trikon-wide invariant, codified in the module docstrings of `trikon.verify.static_checks`, `trikon.verify.local_sandbox`, and `trikon.verify.sandbox`, that a broken sandbox / broken migration / broken tool surfaces as an error past the module boundary, never as a silent success. Requirement 5 pins this contract onto the new State_Migrations_Module.
- **Public_API_Surface**: The set of public symbols consumers depend on across releases: `sdk.verify(...)` signature and return type, the `Verdict` field set, the CLI flag surface (`trikon verify`, `trikon debug verify`, `trikon debug impact`, `--no-sandbox`, `--policy`, `--diff-file`, `--output`, `--base`, `--head`), `LocalSubprocessSandbox.__init__` / `exec` / `mount_repo`, the `Sandbox` union alias, `SandboxExecResult`, and the Static_Baseline_Table column set. All items in Public_API_Surface remain unchanged by this bugfix.

## Requirements

### Requirement 1: The migration fires automatically on the first post-upgrade `_open_state_db` call

**User Story:** As a Trikon user upgrading from ≤ v0.3.4 to v0.3.6, I want `trikon verify` to work correctly on my pre-existing `.trikon/state.db` without me deleting anything, so that I do not observe cache-poisoned counters on the first post-upgrade run.

#### Acceptance Criteria

1. WHEN `Open_State_DB_Site` opens `State_DB`, THE `Open_State_DB_Site` SHALL call `State_Migrations_Module.maybe_migrate_verify_state(conn)` after `ensure_verify_tables(conn)` returns and before the connection is returned to the caller.
2. WHEN `State_Migrations_Module.maybe_migrate_verify_state(conn)` is called on a `State_DB` whose `Schema_Meta_Table` does not contain the key `Verify_Schema_Version`, THE `State_Migrations_Module` SHALL issue `DELETE FROM static_baseline` on the connection, INSERT the row `('verify_schema_version', '1')` into `Schema_Meta_Table`, and COMMIT the two statements as a single atomic transaction.
3. WHERE the initial `run_verification` invocation on an upgraded user's repository would have observed a `Poisoned_Row` on cache-lookup for any `(base_sha, tool, tool_version)` triple, THE `run_verification` invocation SHALL instead observe a cache miss and reconstruct the baseline through the normal `_resolve_base_keys` miss path (`_add_worktree` → `_run_baseline_tool_on_host` → INSERT).
4. WHEN a fresh `State_DB` is created (no prior file at `<repo>/.trikon/state.db`), THE `State_Migrations_Module.maybe_migrate_verify_state(conn)` call from `Open_State_DB_Site` SHALL stamp `Verify_Schema_Version = '1'` into `Schema_Meta_Table` on that fresh DB, so subsequent runs take the fast (idempotent no-op) path from the second invocation onward.
5. THE `State_Migrations_Module.maybe_migrate_verify_state(conn)` SHALL NOT require the caller to have run any command other than a normal `trikon verify` (or `sdk.verify(...)`) invocation — the migration is not gated behind a `trikon cache clear` command, an environment variable, or any explicit user action.
6. WHEN `Open_State_DB_Site` is called from `run_verification` on a `State_DB` whose `Schema_Meta_Table` does not yet exist (a state.db opened by the Verification-Runner before Change-Intelligence has ever run — no `compute_impact` call preceded the `run_verification` call in the caller's process), THE `State_Migrations_Module.maybe_migrate_verify_state(conn)` SHALL idempotently ensure `Schema_Meta_Table` exists by executing `CREATE TABLE IF NOT EXISTS schema_meta (key TEXT PRIMARY KEY, value TEXT NOT NULL)` before its version-marker read, so the migration is callable independently of the Change-Intelligence subsystem's schema init.

### Requirement 2: The migration drops only rows written by pre-v0.3.6 Trikon (schema-marker discipline)

**User Story:** As a Trikon user whose `State_DB` contains correctly-computed baseline rows from a v0.3.6-or-later run interleaved with poisoned rows from a pre-v0.3.6 run, I want the migration to drop only the pre-v0.3.6 rows and preserve the v0.3.6-or-later rows.

#### Acceptance Criteria

1. THE `State_Migrations_Module` SHALL identify a `Poisoned_Row` exclusively by the absence of `Verify_Schema_Version` in `Schema_Meta_Table`, not by inspection of the row's `findings_json` payload, `tool_version` string, `computed_at` timestamp, or any other per-row field.
2. WHEN `State_Migrations_Module.maybe_migrate_verify_state(conn)` observes `Verify_Schema_Version = '1'` already present in `Schema_Meta_Table`, THE `State_Migrations_Module` SHALL return without executing `DELETE FROM static_baseline` and without INSERTing into `Schema_Meta_Table`.
3. WHERE a `State_DB` has been through the migration once (Verify_Schema_Version stamped) and subsequently accumulated rows in `Static_Baseline_Table` through normal `_resolve_base_keys` cache-miss inserts, THE next `State_Migrations_Module.maybe_migrate_verify_state(conn)` call SHALL leave every such row in place — the migration is not re-runnable and does not touch v0.3.6-authored rows.
4. IF a future release bumps `CURRENT_VERIFY_SCHEMA_VERSION` past `1` and ships a v1→v2 migration, THEN the v0.3.6-authored rows tagged by the current migration SHALL remain identifiable as v0.3.6-authored (via the `Verify_Schema_Version` marker they were written under), so the future migration can differentiate v0.3.6 rows from earlier pre-migration rows.
5. WHEN `State_Migrations_Module.maybe_migrate_verify_state(conn)` observes a `Verify_Schema_Version` value that parses to an integer strictly greater than `CURRENT_VERIFY_SCHEMA_VERSION`, THE `State_Migrations_Module` SHALL raise `VerificationRunnerError` with a message naming both the stored version and the running Trikon build's `CURRENT_VERIFY_SCHEMA_VERSION` — the state.db was written by a newer Trikon and this build is not qualified to read from it (parallel to Change-Intelligence's Phase_1_Schema_Version discipline).

### Requirement 3: The migration is idempotent across process invocations

**User Story:** As a Trikon user, I want running `trikon verify` twice in a row to fire the migration exactly once (on the first invocation), so that the second invocation is not slowed down by a redundant scan and does not re-emit the migration notice to my CI logs.

#### Acceptance Criteria

1. WHEN `State_Migrations_Module.maybe_migrate_verify_state(conn)` is called on a `State_DB` whose `Schema_Meta_Table` already contains `Verify_Schema_Version = '1'`, THE `State_Migrations_Module` SHALL execute at most a single `SELECT` against `Schema_Meta_Table` before returning (the version-marker probe), and SHALL NOT execute any `DELETE`, `INSERT`, `UPDATE`, `ALTER`, `DROP`, or `CREATE INDEX` statement.
2. WHEN `State_Migrations_Module.maybe_migrate_verify_state(conn)` is called twice in the same process against the same `State_DB` — once via the first `run_verification` call, once via a hypothetical immediate second call — THE second call SHALL take the fast path from Requirement 3.1 and SHALL NOT emit any log record on `Migration_Notice_Logger`.
3. THE `State_Migrations_Module.maybe_migrate_verify_state(conn)` function SHALL be pure with respect to `Schema_Meta_Table` and `Static_Baseline_Table` when the fast path fires — same inputs, same on-disk state, produce the same (no-op) outputs.
4. WHERE two concurrent processes race to open the same `State_DB` for the first post-upgrade run, THE `State_Migrations_Module` SHALL rely on the SQLite `journal_mode=WAL` + `synchronous=NORMAL` pragmas already applied by `Open_State_DB_Site` and on the atomic `BEGIN IMMEDIATE` / `COMMIT` bracket around the DELETE+INSERT pair, so that the migration fires exactly once per `State_DB` even under concurrent access. A losing racer observes the winning racer's `Verify_Schema_Version` marker on its version-marker probe and takes the fast path.

### Requirement 4: The migration emits a single-line WARNING log record when it drops rows

**User Story:** As a Trikon operator, I want a visible one-line record on the first post-upgrade run naming what the migration did, so that a silent cache clear does not mask a behavior change from me or my CI pipeline.

#### Acceptance Criteria

1. WHEN `State_Migrations_Module.maybe_migrate_verify_state(conn)` executes the `DELETE FROM static_baseline` statement and the delete affects one or more rows, THE `State_Migrations_Module` SHALL emit exactly one log record on `Migration_Notice_Logger` at WARNING level whose message equals `Migration_Notice_Message` with `N` substituted by the actual row count reported by `cursor.rowcount`.
2. WHEN `State_Migrations_Module.maybe_migrate_verify_state(conn)` executes the `DELETE FROM static_baseline` statement and the delete affects zero rows (a fresh `State_DB` on first-run — no poisoning to clean, just the marker to stamp), THE `State_Migrations_Module` SHALL NOT emit any log record on `Migration_Notice_Logger`.
3. THE `Migration_Notice_Logger` SHALL be the module logger obtained via `logging.getLogger("trikon.verify.state_migrations")`. THE `State_Migrations_Module` SHALL NOT write directly to `sys.stdout` or `sys.stderr`; STDERR emission is delegated to the caller's `logging` handler configuration.
4. THE `Migration_Notice_Message` SHALL name (a) the running Trikon version obtained via `trikon.__version__`, (b) the count of rows dropped from `Static_Baseline_Table`, and (c) a reference to this spec by kebab-case name (`static-baseline-cache-poisoning-migration`) so a future maintainer grepping for the log line can locate the spec.
5. WHERE the caller has configured Python's `logging` module with a handler that captures WARNING-level records (Trikon's CLI default), THE `Migration_Notice_Message` SHALL appear on STDERR of the `trikon verify` invocation exactly once per migration event.
6. THE `Migration_Notice_Logger` invocation SHALL use the `%s`-style logging idiom (`logger.warning("… %s …", value)`) rather than pre-formatted f-strings, so that a WARNING-suppressed handler pays no string-formatting cost.

### Requirement 5: The migration preserves the Never_Fail_Open_Contract

**User Story:** As a Trikon maintainer, I want any failure inside the migration (a locked SQLite database, a disk-full error, a corrupt `Verify_Schema_Version` value) to surface as a loud `VerificationRunnerError` past `sdk.verify(...)`, not as a silent success on a still-poisoned cache.

#### Acceptance Criteria

1. IF the `SELECT value FROM schema_meta WHERE key = 'verify_schema_version'` probe raises `sqlite3.Error` (locked database, disk read error, corrupt journal, etc.), THEN THE `State_Migrations_Module` SHALL raise `VerificationRunnerError` with `raise ... from exc` preserving the underlying `sqlite3.Error` on `__cause__`.
2. IF the `DELETE FROM static_baseline` statement raises `sqlite3.Error`, THEN THE `State_Migrations_Module` SHALL raise `VerificationRunnerError` with `raise ... from exc` preserving the underlying `sqlite3.Error` on `__cause__` and SHALL NOT stamp `Verify_Schema_Version` into `Schema_Meta_Table` (leaves the DB in the pre-migration state so a retry can attempt the migration again cleanly).
3. IF the `INSERT INTO schema_meta` statement (writing the `Verify_Schema_Version` marker) raises `sqlite3.Error`, THEN THE `State_Migrations_Module` SHALL raise `VerificationRunnerError` with `raise ... from exc` preserving the underlying `sqlite3.Error` on `__cause__`; the enclosing `BEGIN IMMEDIATE`/`COMMIT` transaction SHALL be rolled back so the preceding DELETE does not partially land.
4. IF the stored `Verify_Schema_Version` value cannot be parsed as an integer (a corrupt row written by an out-of-tree caller directly manipulating `Schema_Meta_Table`), THEN THE `State_Migrations_Module` SHALL raise `VerificationRunnerError` naming the offending value on `__cause__` via `ValueError`, matching Phase 1's `DepGraph._init_schema` handling of a corrupt `schema_version`.
5. THE `State_Migrations_Module` SHALL NOT silently proceed with a poisoned cache under any failure mode — the migration either succeeds atomically (DELETE + INSERT committed together, or nothing) or raises `VerificationRunnerError`.
6. WHEN `State_Migrations_Module.maybe_migrate_verify_state(conn)` raises `VerificationRunnerError`, THE `Open_State_DB_Site` SHALL close the connection before re-raising, matching the existing failure-path handling for `ensure_verify_tables` (`Open_State_DB_Site` currently closes the connection when `ensure_verify_tables` raises).

### Requirement 6: The bugfix does not change the Public_API_Surface

**User Story:** As a downstream Trikon consumer (a CI plugin, an SDK caller, a policy-configuration author), I want the v0.3.5 → v0.3.6 upgrade to be a drop-in — no API changes, no new required parameters, no changed field names.

#### Acceptance Criteria

1. THE `sdk.verify(*, repo, base_sha=None, head_sha=None, diff=None, policy_path=".trikon/policy.yaml", cache_db=None, no_sandbox=False) -> Verdict` signature SHALL remain unchanged by this bugfix — no new parameter, no removed parameter, no changed default.
2. THE `Verdict` field set SHALL remain unchanged by this bugfix — the fields `decision`, `reason`, `matched_rule`, `warnings`, `evidence`, `audit_id`, `schema_version` all keep their v0.3.5 shape and semantics.
3. THE CLI flag surface on `trikon verify`, `trikon debug verify`, and `trikon debug impact` SHALL remain unchanged by this bugfix — no new flag, no removed flag, no changed help text (beyond an optional docstring mention of the migration; the CLI options table is untouched).
4. THE `Static_Baseline_Table` column set SHALL remain `(id, base_sha, tool, tool_version, findings_json, computed_at)` after this bugfix — no `ALTER TABLE ADD COLUMN`, no column rename, no column drop. The version-marker discipline lives in `Schema_Meta_Table`, not in `Static_Baseline_Table`.
5. THE `trikon.verify.db.ensure_verify_tables(conn)` function SHALL remain additive-only as specified in its module docstring — only `CREATE TABLE IF NOT EXISTS` and `CREATE INDEX IF NOT EXISTS` statements, no `ALTER`/`DROP`. The migration's DELETE+INSERT is not DDL and is hosted in a separate module.
6. THE `LocalSubprocessSandbox.__init__`, `LocalSubprocessSandbox.exec`, and `LocalSubprocessSandbox.mount_repo` signatures SHALL remain unchanged by this bugfix.
7. THE `Sandbox` union alias exported from `trikon.verify.sandbox` SHALL remain `LocalDockerSandbox | LocalSubprocessSandbox` — unchanged.
8. THE `SandboxExecResult` fields `exit_code`, `stdout`, `stderr`, `duration_ms`, `timed_out` SHALL remain unchanged by this bugfix.
9. THE new public function `trikon.verify.state_migrations.maybe_migrate_verify_state(conn: sqlite3.Connection) -> None` SHALL be typed with the concrete `sqlite3.Connection` parameter type and a `None` return — no `dict[str, Any]` appears on the signature, matching the project-wide `dict[str, Any]` prohibition on public API surfaces.
10. THE `State_Migrations_Module` public surface SHALL be limited to `maybe_migrate_verify_state`, `CURRENT_VERIFY_SCHEMA_VERSION`, and `__all__`; no other symbol SHALL be exported from the module. `MigrationError`-style bespoke exception classes SHALL NOT be introduced — every raise site uses `VerificationRunnerError` from `trikon.verify.errors`.

### Requirement 7: The migration is testable at the SQLite level without a running Docker daemon

**User Story:** As a Trikon maintainer, I want unit tests that exercise every migration branch (fresh-DB stamp, poisoned-DB drop-and-stamp, already-migrated no-op, corrupt-value raise, sqlite-error raise) using an in-memory SQLite connection, so that the fix is anchored against regression without depending on a Docker daemon, a real click clone, or a real ruff/mypy binary.

#### Acceptance Criteria

1. WHEN a unit test creates an in-memory `sqlite3.Connection` (`sqlite3.connect(":memory:")`), applies the Phase-1 pragmas, calls `ensure_verify_tables(conn)`, seeds a `Poisoned_Row` into `Static_Baseline_Table` with `findings_json = '[]'` and any `(base_sha, tool, tool_version)` triple, and then invokes `State_Migrations_Module.maybe_migrate_verify_state(conn)`, THE unit test SHALL be able to assert that `SELECT COUNT(*) FROM static_baseline` returns `0` and `SELECT value FROM schema_meta WHERE key = 'verify_schema_version'` returns `'1'`.
2. WHEN a unit test seeds `Verify_Schema_Version = '1'` into `Schema_Meta_Table` on an in-memory connection and populates `Static_Baseline_Table` with a v0.3.6-authored row, then invokes `State_Migrations_Module.maybe_migrate_verify_state(conn)`, THE unit test SHALL be able to assert that the row remains present (fast-path idempotence).
3. WHEN a unit test patches `sqlite3.Connection.execute` (or an equivalent injected connection wrapper) to raise `sqlite3.Error` on the DELETE statement, THE `State_Migrations_Module.maybe_migrate_verify_state(conn)` call SHALL raise `VerificationRunnerError` whose `__cause__` is the injected `sqlite3.Error`.
4. WHEN a unit test seeds a corrupt `verify_schema_version` value (e.g., `'not-an-int'`) into `Schema_Meta_Table`, THE `State_Migrations_Module.maybe_migrate_verify_state(conn)` call SHALL raise `VerificationRunnerError` whose message names the corrupt value.
5. THE unit tests SHALL run under `pytest` inside `tests/unit/verify/` and SHALL NOT require Docker, a network connection, a real click clone, a real ruff / mypy binary, or any host state outside the in-memory SQLite fixture.
6. THE unit tests SHALL cover the never-fail-open contract (Requirement 5) by asserting the outward exception type is `VerificationRunnerError` on every simulated failure, not `sqlite3.Error` leaking through unwrapped.

### Requirement 8: The migration is verifiable end-to-end against the Click_Repro

**User Story:** As a Trikon release engineer, I want the v0.3.5 checkpoint's poisoning-then-clean scenario to reproduce end-to-end on the v0.3.6 build so I have confidence the migration closes the trap that the checkpoint discovered.

#### Acceptance Criteria

1. WHEN a scratch `State_DB` at `~/click/.trikon/state.db` is seeded with one or more `Poisoned_Row` entries (any `(base_sha, tool, tool_version)` triple, `findings_json = '[]'`) and no `Verify_Schema_Version` key in `Schema_Meta_Table`, then `trikon verify --repo ~/click --base 87f7a31 --head 6aabf09 --no-sandbox` is invoked against a locally-built v0.3.6 wheel, THE first invocation SHALL emit the `Migration_Notice_Message` on STDERR, THE returned `Verdict` SHALL satisfy `decision == "block"`, `matched_rule == "new static-analysis errors"`, `evidence.verification.static.new_errors == 33`, `evidence.verification.static.new_warnings == 8`, `evidence.verification.static.preexisting_errors == 97`.
2. WHEN the same `trikon verify --no-sandbox` invocation is repeated (second call on the now-migrated `State_DB`), THE second invocation SHALL NOT emit the `Migration_Notice_Message` on STDERR AND SHALL return a `Verdict` whose counters compare equal to the first invocation's counters.
