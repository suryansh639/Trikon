# Implementation Plan: static-baseline-cache-poisoning-migration

## Overview

Bugfix for Trikon v0.3.5, targeting the v0.3.6 release. A user upgrading from Trikon ≤ v0.3.4 to v0.3.5 with a pre-existing `<repo>/.trikon/state.db` observes cache-poisoned counters on the first post-upgrade `trikon verify --no-sandbox` invocation: the `static_baseline` table carries rows written by pre-v0.3.5 code with `findings_json = '[]'`, and v0.3.5's fixed head-side finding-diff classes every real head finding as `is_new=True` against that empty baseline. Verified on the pallets/click repro (base `87f7a31`, head `6aabf09`): with pre-v0.3.5 state.db present, v0.3.5 `--no-sandbox` returns `new_errors=130, preexisting_errors=0`; after `rm .trikon/state.db`, the ground truth `new_errors=33, new_warnings=8, preexisting_errors=97` is restored on both backends.

Fix strategy (from clarify phase): schema-version bump + `DELETE FROM static_baseline` on migration, hosted in a new `trikon.verify.state_migrations` module and hooked into `trikon.verify.runner._open_state_db` immediately after `ensure_verify_tables(conn)`. The migration reads a Phase-2 version marker at `schema_meta.verify_schema_version` (independent of Phase-1's `schema_meta.schema_version`). On a marker-absent state.db, the migration DELETEs every row from `static_baseline`, INSERTs `verify_schema_version = '1'`, commits atomically, and — when the delete affected ≥1 row — emits a single-line WARNING record on `logging.getLogger("trikon.verify.state_migrations")` naming the row count and referencing this spec. On a marker-present state.db, the migration is a single-SELECT fast-path no-op. Every `sqlite3.Error` wraps as `VerificationRunnerError` with `raise ... from exc`; the migration is atomic (DELETE+INSERT commit together or roll back together). No changes to public API, no changes to `static_baseline` columns, no changes to `ensure_verify_tables`'s additive-only invariant. See design.md §3-§4 for the full surface.

Convert the feature design into a series of prompts for a code-generation LLM that will implement each step with incremental progress. Make sure that each prompt builds on the previous prompts, and ends with wiring things together. There should be no hanging or orphaned code that isn't integrated into a previous step. Focus ONLY on tasks that involve writing, modifying, or testing code.
