# Implementation Plan: trikon-cloud-webhook-receiver-installation-events

## Overview

Amendment to Spec 1's `Webhook_Receiver` (`.kiro/specs/trikon-cloud-webhook-receiver/`) that extends the 13-path never-fail-open decision tree to 15 paths by inserting a second enqueue branch for GitHub App installation-lifecycle deliveries (`installation` and `installation_repositories`). Validated payloads are mapped to Spec 3's `InstallationEventMessage` and enqueued on the `trikon-cloud-installation-events` SQS queue owned by Spec 3's `OrchestratorStack`; the queue is imported by ARN, not created here. Ships edits to five source files (`models.py`, `sqs_writer.py`, `handler.py`, `infra/webhook_receiver_stack.py`, `infra/app.py`) and one new dedicated test file (`tests/test_installation_events_routing.py`). Zero modifications to `hmac_verifier.py`, `logger.py`, any Spec 3 module, or Spec 3's `OrchestratorStack` synthesized output. Zero new runtime or dev dependencies.

Execution proceeds in four waves. **Wave 0** (tasks 1-2) lands the two leaf-module extensions in parallel — `models.py` gains three new Pydantic classes plus an env-config field, and `sqs_writer.py` gains a `send_installation_event` method backed by a shared `_send_body` helper. Both touch disjoint files and share no state. **Wave 1** (tasks 3-5) lands the handler rewire plus the two CDK edits in parallel; each of the three files is disjoint from the other two. **Wave 2** (task 6) adds the dedicated test file, which reads all Wave 0 and Wave 1 changes end-to-end. **Wave 3** (task 7) is the completion checkpoint: pytest (64+ tests, 49 pre-existing + ~18 new), mypy `--strict`, ruff clean, and a coverage assertion on `handler.py` (≥90% line coverage).

Convert the feature design into a series of prompts for a code-generation LLM that will implement each step with incremental progress. Make sure that each prompt builds on the previous prompts, and ends with wiring things together. There should be no hanging or orphaned code that isn't integrated into a previous step. Focus ONLY on tasks that involve writing, modifying, or testing code.

## Wave-based execution plan

- **Wave 0 — Foundation:** tasks 1 and 2, parallelizable — the `models.py` extension and the `sqs_writer.py` extension touch disjoint files and share no state. Neither reads from the other.
- **Wave 1 — Handler + CDK:** tasks 3, 4, and 5, parallelizable — `handler.py`, `infra/webhook_receiver_stack.py`, and `infra/app.py` are three disjoint files. All three depend on Wave 0 (handler consumes the new models and the new `send_installation_event` method; the CDK stack plumbs the queue URL that the handler's `ReceiverEnvConfig` now requires).
- **Wave 2 — Tests:** task 6 — the dedicated test file exercises the extended handler end-to-end against moto-backed SQS + Secrets Manager. Depends on Wave 1.
- **Wave 3 — Checkpoint:** task 7, verification only — pytest, mypy `--strict`, ruff, and a coverage floor check on `handler.py`.
