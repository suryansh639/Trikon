# Implementation Plan: no-sandbox-cache-dir-strip

## Overview

Bugfix for Trikon v0.3.4, targeting the v0.3.5 release. `trikon.verify.local_sandbox.LocalSubprocessSandbox.exec` is the `--no-sandbox` head-side backend that runs ruff / mypy directly on the host through `subprocess.run`. The argv it receives is produced by `run_static_checks` from `DEFAULT_STATIC_TOOLS`, which pins `--cache-dir=/workspace/tmp/.ruff_cache` and `--cache-dir=/workspace/tmp/.mypy_cache` (v0.3.3 "Bug F" fix — those paths only exist inside the Docker sandbox's writable tmpfs at `/workspace/tmp`). On the host filesystem `/workspace/tmp` does not exist (and on Windows is not even a valid path), so ruff / mypy fail cache init silently and produce empty output. Result: `evidence.verification.static.findings == []` on the `--no-sandbox` path even when the Docker path returns 100+ real findings on the same diff (WSL Property 3 verification against pallets/click base `87f7a31` → head `6aabf09` — Docker returns `decision=block, new_errors=33, new_warnings=8, preexisting_errors=97`; `--no-sandbox` returns `decision=require_human, matched_rule=default, all counters 0`).

The mirror function `trikon.verify.static_checks._run_baseline_tool_on_host` already carries the fix — a single-line strip `argv = tuple(t for t in argv if not t.startswith("--cache-dir="))` applied right after `_expand_argv` produces the argv tuple (v0.3.3, alongside the sandbox-side pin). `LocalSubprocessSandbox.exec` is the twin raise site for the head-side host-subprocess path, and it has NO such strip. The fix is symmetric: apply the same one-line strip at the top of `exec` (right after the `self._active` guard, before the `_resolve_workdir` call and before the venv-PATH prepend / `shutil.which` argv[0] resolution). Include an inline comment naming the mirror function `_run_baseline_tool_on_host`, the v0.3.3 Bug F fix, and the sandbox-only `/workspace/tmp` prefix so a future maintainer can grep between the two strip sites.

`LocalSubprocessSandbox.__init__`, `LocalSubprocessSandbox.exec`, `LocalSubprocessSandbox.mount_repo`, the `Sandbox` union alias, and `SandboxExecResult` are all unchanged in signature and public shape. `DEFAULT_STATIC_TOOLS` is unchanged (the sandbox path continues to need the flag). The change is entirely internal to `LocalSubprocessSandbox.exec`.

Convert the feature design into a series of prompts for a code-generation LLM that will implement each step with incremental progress. Make sure that each prompt builds on the previous prompts, and ends with wiring things together. There should be no hanging or orphaned code that isn't integrated into a previous step. Focus ONLY on tasks that involve writing, modifying, or testing code.
