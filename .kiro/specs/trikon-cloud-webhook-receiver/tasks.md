# Implementation Plan: trikon-cloud-webhook-receiver

## Overview

M1 net-new component of Trikon Cloud — the GitHub webhook receiver. Ships a Python 3.11 AWS Lambda function fronted by an API Gateway HTTP API that verifies HMAC-SHA256 signatures on `POST /webhooks/github`, routes on `X-GitHub-Event`, and enqueues jobs on the `trikon-verify-jobs` SQS queue for the downstream Fargate runner (Spec 2) and orchestrator (Spec 3) to consume. Grounding reference: `.kiro/specs/trikon-cloud-architecture/design.md` §3.2 (Lambda control plane), §3.3 (SQS shape), §3.5 (secrets), §3.8 (us-east-1), §3.9 (no VPC), §5.1 (webhook payload subset), §5.2 (SQS body), §6 (security model), plus cross-cutting Invariants 1, 2, 3, 6, 7, 8.

Tech stack (per design.md §3): Python 3.11 on Lambda, `aws-lambda-powertools[all]` for the HTTP resolver, `pydantic>=2` for models, `boto3` for SQS + Secrets Manager, `pytest` + `moto` + `hypothesis` + `pytest-cov` for tests, AWS CDK (Python) for IaC. Package location: `trikon_cloud/webhook_receiver/` — a new top-level package inside the Trikon monorepo, sibling of `trikon/`. Added to `pyproject.toml` under a new `cloud` optional-dep group so `uv sync --extra cloud` bootstraps the receiver's dependency set without disturbing the SDK's runtime dependencies.

Wave partitioning: Wave 0 lands the package skeleton and dependency wiring (foundation for all Python imports). Wave 1 lands the five production Python modules in parallel where possible (`models.py`, `hmac_verifier.py`, `sqs_writer.py`, `logger.py` are independent leaves; `handler.py` depends on all four). Wave 2 lands the unit tests including the three correctness properties from design.md §6. Wave 3 lands the CDK stack, app entry, and deploy README. The checkpoint runs the local end-to-end integration harness plus the mypy / ruff / pytest quality gates.

Convert the feature design into a series of prompts for a code-generation LLM that will implement each step with incremental progress. Make sure that each prompt builds on the previous prompts, and ends with wiring things together. There should be no hanging or orphaned code that isn't integrated into a previous step. Focus ONLY on tasks that involve writing, modifying, or testing code.

  - [x] 2.2 Create `trikon_cloud/webhook_receiver/hmac_verifier.py`. Declare `__all__ = ["verify_signature"]` at module top. Import `hmac` and `hashlib` from the stdlib. Implement the pure function `def verify_signature(body: bytes, signature_header: str | None, secret: bytes) -> bool` per design.md §4 (module responsibilities). Algorithm: (a) if `signature_header is None` or empty → return `False`; (b) if `signature_header` does not start with the literal prefix `"sha256="` → return `False`; (c) parse the digest via `signature_header.removeprefix("sha256=")`; (d) if the parsed digest length is not exactly 64 or contains any non-hex character → return `False` (test via `int(parsed, 16)` inside a `try / except ValueError` — on `ValueError`, return `False`); (e) compute `expected = hmac.new(secret, body, hashlib.sha256).hexdigest()`; (f) return `hmac.compare_digest(parsed, expected)`. The function MUST NOT log, MUST NOT raise on any input in the domain of `(bytes, str | None, bytes)` (Property 1 is a totality claim), and MUST NOT use `==` between the parsed digest and the computed digest (Property 3 is a source-level invariant). Add a module docstring naming Property 1 and Property 3 from design.md §6. Verify with `uv run mypy --strict trikon_cloud/webhook_receiver/hmac_verifier.py` and `uv run ruff check trikon_cloud/webhook_receiver/hmac_verifier.py`.

## Notes

- Tasks marked with `*` (specifically 3.2, 3.3, 3.4, 3.5) are the test tasks and are technically optional for a bare-minimum MVP. They are STRONGLY RECOMMENDED even for MVP — task 3.2 encodes Property 1 (HMAC verification is total) and Property 3 (constant-time comparison — a source-level invariant), and task 3.3 encodes Property 2 (every 202 has a preceding successful SQS send). These properties are the cross-cutting-invariant guardrails for Invariant 2 (never-fail-open) and Invariant 6 (secrets handling). Skipping them means shipping a webhook receiver without an automated check that HMAC verification runs in constant time — a security regression that would surface only under a timing-attack red-team scenario. Do not skip.
- Wave 0 (task 1) lands the package skeleton and `pyproject.toml` wiring. Wave 1 (task 2) lands the production Python modules — sub-tasks 2.1, 2.2, 2.3, 2.4 write independent leaf files; 2.5 depends on all four. Wave 2 (task 3) lands the tests — 3.1 (conftest) is the leaf; 3.2, 3.3, 3.4, 3.5 depend on 3.1 AND on the production modules from Wave 1. Wave 3 (task 4) lands the CDK IaC — 4.1 (stack), 4.2 (app entry, depends on 4.1), 4.3 (README).
- Task 5 is the checkpoint. It runs the local integration harness and the mypy / ruff / pytest / coverage gates. Passing task 5 means the spec is code-complete; failing task 5 means returning to a prior Wave.
- Product name is **Trikon** throughout the deliverable code. The service label in the powertools Logger is `trikon-cloud-webhook-receiver` (identifier — acceptable per Invariant 7). The CDK stack class is `WebhookReceiverStack` (identifier). The queue name is `trikon-verify-jobs` (identifier). No user-facing string in this spec surfaces AgentGuard or any variant.
